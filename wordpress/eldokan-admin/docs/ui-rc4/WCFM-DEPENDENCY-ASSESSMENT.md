# تقييم الاعتماد على WCFM وخطة الاستقلال — RC4

**مراجعة مصدر للقراءة فقط؛ ليست تصريحًا لتعطيل WCFM.** لم نعدّل Admin migrations أو الواجهات أو قواعد البيانات. مصادر التجار والعملاء المرفقة مع الإضافة الأخيرة مطابقة SHA256 للنسخ التي سبق فحصها، فاستُخدمت النتائج دون إعادة تدقيق تاريخي.

المصادر: Admin Staff 1.10.0-rc.3 ثم rc.4؛ Seller API 1.75.70-rc.1؛ Customer API 0.10.0؛ Client 0.8.2-rc.2. ملف INPUT-PROVENANCE.json يثبت المدخلات. شفرة WCFM وإضافات الشحن/السحب الفعلية وقاعدة بيانات المتجر لم تُقدّم؛ أي استنتاج عن استخدامها الحي يحتاج تحققًا منفصلًا.

## نتائج منفذة وحدودها

`known-api-ownership-gaps.json` يستدعي resolver الحقيقي في اللقطتين باستخدام بيانات مصطنعة: مالك canonical=7 وcreator=99 أعطى Seller=99 وCustomer=sel_7. قد يكون creator عضوًا في نفس فريق المالك في الواقع؛ الاختبار يثبت اختلاف الأولوية، ولا يثبت اختلاف المالك النهائي لكل منتج حي. سطر canonical=7 بلا منتج/variation لم يتعرف عليه resolver الخاص بالتاجر. لا توجد كتابة لهذه البيانات أو تعديل للواجهات.

لم تُرصد استدعاءات classes أو functions من WCFM في الفحص الموجّه لـSeller/Customer API، بخلاف اعتماد metadata/roles والفروع الموضحة أعلاه. لا تعني هذه الملاحظة أن التشغيل الحي لا يطلق hooks مسجلة من WCFM داخل Woo. `api-dependency-hits.txt` يحفظ مواضع البحث، ومصفوفة العميل في customer-client-compatibility.json تطابق 65 عملية، بما فيها /stories من Admin.

## هل يمكن إخفاء شاشات WCFM القديمة؟

**يمكن اقتراح إخفاء روابط قائمة محددة فقط بعد قبول بديلها وظيفيًا وصلاحيًا. لم تُخفَ أي شاشة WCFM في RC4.** الحفاظ على تحميل الإضافة وREST/AJAX/cron/classes/hooks/services شرط. إخفاء القائمة ليس إجراء أمان ولا دليل استقلال. شاشات السحب والتسويات وإعداد طرق الشحن والسياسات لا تُرشح للإخفاء حتى جرد الاستخدام ومراجعة الموظفين. لا توجد قائمة slugs موثوقة يمكن اعتمادها دون نسخة WCFM المركبة وملحقاتها.

## وظائف خلفية وبيانات لازمة قبل الاستقلال

- توحيد resolver للمالك عبر Admin/Seller/Customer مع alias للمنتجات المترجمة والـvariations، وحفظ مالك غير قابل للفقد على كل سطر طلب وتاريخ تحوّل الملكية.
- تصنيف الأدوار والحسابات والأعضاء؛ جدول mapping قابل للعكس يحفظ user IDs والأدوار السابقة والمصدر. لا يكفي تبديل wcfm_vendor إلى eldokan_owner بالجملة.
- خرائط store metadata والسياسات والعناوين والشحن، مع version ومصدر كل قيمة وحل تعارض واعتماد copy-first.
- دفتر عمليات مالي idempotent: مستحقات/عمولات/ضرائب/خصومات/refunds/حجوزات/تسويات/سحب/تسوية البنك، مع سجلات مدققة وربط تاريخ WCFM. لا تُحوّل قيمة net الحالية إلى رصيد افتتاحي دون مطابقة.
- بديل مثبت لتجزئة سلة متعددة التجار وحزم الشحن وتكاليفها والمناطق والتتبع إن كان WCFM يوفرها حاليًا؛ Bosta مؤجل في المصادر الحالية وليس بديلًا منفذًا.
- سياسة تنفيذ الإرجاع عبر التاجر والإدارة وربط الاسترداد وإلغاء العمولة وأثره على التسوية. نموذج طلب العميل وحده لا ينفذ هذه الدورة.

هذه متطلبات مستقبلية وليست migrations أضيفت لهذا الإصدار. عدد الجداول/الصفوف والمبالغ وسرعة الترحيل لا يمكن تقديرها بدقة من المصدر وحده.

## خطة مرحلية وبوابات خروج

| المرحلة | العمل المستقبلي | معيار خروج قابل للقياس | الرجوع |
|---|---|---|---|
| 0: تثبيت الواقع | جرد نسخة WCFM/ملحقاتها/hooks/cron/caps ومستخدميها وبياناتها على staging | inventory موقع وبصمات وتغطية كل خدمة مستعملة؛ WCFM مفعّل | لا تغيير للخدمة |
| 1: هوية موحدة | معالجة اختلافَي resolver، وتوثيق canonical order items والمتاجر والترجمات | صفر تعارض ملكية غير محسوم في snapshot كامل؛ حفظ جميع IDs | mapping قديم محفوظ وتراجع flags |
| 2: قراءة ظل | بناء adapters قراءة ElDokan ومقارنة الاستعلامات دون تبديل الكتابة | تطابق عدد الحسابات والمنتجات والطلبات، وتقارير فروق مفسرة لكل سجل | الرجوع لقراءة legacy |
| 3: مال وشحن وإرجاع | تنفيذ النواقص في checkpoint مستقل مع سجلات وحسابات موثقة | صفر فرق مالي غير مفسر حسب العملة/الفترة؛ نجاح multi-seller/refund/partial-refund/payout/shipping/returns | snapshots ودفتر compensating entries؛ لا حذف مالي |
| 4: انتقال مضبوط | نسخ بيانات idempotent على دفعات ثم shadow/feature flags | عقود REST ثابتة، لا تسرب ملكية، قياسات أداء وقبول تشغيل؛ إعادة الدفعة لا تكرر بيانات | revert flags وإبقاء المصدر الأصلي |
| 5: تقليل الواجهة ثم الخدمة | إخفاء شاشات legacy المقبولة أولًا؛ تعطيل WCFM لاحقًا بتصريح مستقل | فترة مراقبة معتمدة، لا hooks/services ناقصة، تجربة rollback ناجحة ونسخة احتياطية | إعادة WCFM وخدماته مع استعادة متسقة |

Seller API يحتاج مراجعة مخصصة لاحقًا لحدود الفريق ووراثة المالك، order-item canonical، المزامنة الزمنية للرسوم، الشحن والتسويات. لم نوسّع التنفيذ إلى تلك المواضيع هنا.

### اعتماد مشترك مثبت إضافي

Customer Orders يضيف canonical seller على `woocommerce_checkout_create_order_line_item` بأولوية PHP_INT_MIN، وAdmin يسجل `snapshot_order_item_fee_rule` على الخطاف نفسه بأولوية 30. إذن لقطة رسوم الشراء تمر أيضًا من Admin عند تفعيله؛ لا توجد كتابة fee_snapshot مباشرة داخل Customer API. قارئا التقارير في Admin وSeller يستهلكان اللقطة أو fallback إلى القواعد الحالية. الحفاظ على تحميل Admin وترتيب هذا الخطاف شرط قبول اللقطات؛ هذا اعتماد على ElDokan/Woo مستقل عن اسم WCFM، وليس دليلًا على استقلال التقارير إذا عُطلت Admin.
