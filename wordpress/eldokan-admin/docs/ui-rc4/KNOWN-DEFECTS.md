## باقية وتمنع اعتمادًا ماليًا/تكامليًا

### K1 — ملخصات مالية محدودة ومختلفة التعريف

الملف `includes/class-eldokan-admin.php`، الدوال `overall_metrics`, `seller_order_metrics`, `all_orders`. تستعمل أحدث ٣٠٠ طلب قبل تصفية التاريخ، تجمع البنود لجميع الحالات وتستخدم قواعد العمولة الحالية. نموذج ٣٢٠ طلبًا أثبت العد ٣٠٠، بينما التقرير المفصل مرّ على ٣٢٠ وميّز المدفوع والمرتجع. لم تُغير الحسابات تنفيذًا لقيد الحفاظ على المنطق المالي؛ أزيل الإيحاء بأنها إيرادات أو رصيد معتمد. يلزم checkpoint لتعريف المؤشرات واختبارات مالية ومطابقة فعلية.

### K2 — اختلاف أولوية منشئ المنتج ومالكه في لقطتي API

نسخة Seller API 1.75.70-rc.1 المتاحة: `marketplace_product_seller_user_id` في `includes/class-eldokan-dashboard-api.php` يفضل `_eldokan_created_by` قبل `_eldokan_seller_user_id`. نسخة Customer API 0.10.0 المتاحة: `ElDokan_Customer_API_Sellers::for_product` يعتمد المفتاح الثاني فقط. نموذج بمالك ٧ ومنشئ ٩٩ أعاد ٩٩ للتاجر وsel_7 للعميل. قد يصح الربط إذا كان المنشئ عضوًا تابعًا لنفس المالك؛ لا يجوز افتراض ذلك لكل البيانات. يلزم تطابق هوية canonical عبر الواجهتين واختبار المستخدم الموظف/المدير. لم تُعدل الواجهتان.

### K3 — بند طلب canonical فقط مع منتج غير متاح

`order_item_belongs_to_group_safe` في Seller API المتاح لا يفحص `_eldokan_seller_user_id` ضمن مفاتيح البند القديمة؛ يعتمد بعدها على المنتج. Customer API Orders يكتب هذا المفتاح على البند، وAdmin يقرأه أولًا. نموذج بند بالمفتاح ٧ ومعرّف منتج غير متاح أعاد false من محلل Seller API. الأثر المحتمل: اختفاء تاريخ طلب/مبلغ من واجهة التاجر عندما لا يوجد بديل قديم أو منتج صالح. لم نثبت حدوثه في Live. يلزم إصلاح متوافق داخل Seller API بمرحلة منفصلة، واختبارات منتج محذوف/variation ومرتجع وطلبات قديمة.

### K4 — حدود الأرقام والتوقيت واللغات

عد العملاء هو مستخدمو customer/subscriber وليس عدد مشترين يشمل الزوار. عد التجار حسب الأدوار وليس عدد شركات مميزًا بالضرورة. عد المنتجات native posts وقد يضم ترجمات؛ التصفية الفعلية لـWPML لم تختبر. استدعاءات strtotime/current_time مقابل WC dates تحتاج قبول حدود اليوم والتوقيت الصيفي. بعض قوائم التجار/ملف التاجر لها حدود استعلام قديمة. لم تُعد كتابة هذه العلاقات أو الاستعلامات.

### K5 — لا إثبات لخدمات السوق الكاملة

صافي التاجر في التقرير ليس رصيدًا دفتريًا قابلًا للصرف. لم نجد خدمة سحب/تسوية مثبتة في مسارات المصدر التي فُحصت، ولم تتوفر مصادر WCFM المثبتة ومخطط قواعده الحية. لا يمكن إيقافه اعتمادًا على اكتمال فهرسة الملكية.

### K6 — ملاحظات عرض ومرجع العميل

رسم Distribution يجمع مقاييس غير متجانسة، ونصوص EGP موروثة لا تثبت دعمًا متعدد العملات. README الخاص بعميل API يحتفظ بعبارة إصدار تاريخية قديمة رغم package.json وRC2-INTEGRATION الحاليين. لم تُعدل حسابات الرسم أو مصدر العميل.

## غير منفذ أو غير مقبول بعد

بيئة WordPress كاملة مع DB وWooCommerce/HPOS/WPML/WCFM/Paymob، حفظ/حذف وتصدير فعلي، CRUD وإرسال البريد الحي، قراءة الجلسات والشحن والدفع، واختبارات قارئ الشاشة/هندسة المتصفح. ملفات النماذج وصور العارض الثابت ليست إثباتًا لهذه العمليات.

خلال تجهيز أدوات الاختبار ظهرت نواقص في stubs مثل edit_term ونوع WC_Order_Item_Product ثم صُححت النماذج؛ ليست عيوبًا منسوبة للإضافة. النتائج النهائية والعيوب الأصلية المؤكدة منفصلة في ملفات الأدلة.
