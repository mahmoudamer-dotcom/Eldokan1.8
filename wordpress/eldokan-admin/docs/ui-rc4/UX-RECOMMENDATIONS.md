# توصيات تجربة الاستخدام اللاحقة

لم تنفذ البنود التالية؛ التنفيذ الحالي محصور في واجهة Admin وقيودها. ليست موافقة ضمنية على وظائف جديدة.

| الأولوية | الملاحظة المثبتة | التحسين المقترح والنطاق |
|---|---|---|
| عالية | ملخص 300 ورسم Distribution يخلط أنواع عد مختلفة؛ نصوص EGP موروثة | اعتماد قاموس KPIs وفترة/حالات/عملة موحدة، ثم استبدال الرسم بصف مؤشرات متجانسة. تغييرات الحساب تحتاج قبولًا ماليًا منفصلًا |
| عالية | اختلاف resolvers الملكية وسطر canonical بلا منتج في Seller API | checkpoint إصلاح backend قبل الاعتماد على تطابق واجهات الإدارة والتاجر والعميل؛ لا يحل بالتجميل |
| عالية | قائمة Orders تجمع وتفلتر batches في PHP؛ بعض selectors لها حدود قديمة | تصميم استعلامات server filters وفهرسة قابلة للقياس، مع حفظ العقود واختبار HPOS؛ ليس ضمن تعديل العرض الحالي |
| متوسطة | ملف التاجر يحوي مجموعات عمل كثيرة رغم الطي الاختياري الجديد | قبول مستخدمين لتقسيم الحسابات/المنتجات/المالية والروابط المثبتة قبل تحويله إلى tabs أو fetch حسب الحاجة |
| متوسطة | بعض رسائل الوحدات القديمة والـconfirm والرسم ما زالت نصوصًا مختلطة | استكمال gettext وتوحيد رسائل الخطأ والتأكيد داخل كل وحدة على حدة، دون تغيير handlers |
| متوسطة | Chart.js من CDN موروث | مراجعة ترخيص وتضمين نسخة محلية أو رسم أبسط قابل للقراءة دون Canvas؛ لا اعتماد مكتبة أو تنزيل جديد هنا |
| لاحقة | صلاحيات الموظفين ومفاهيم view/manage واسعة للمستخدم غير التقني | تجربة شرح الصلاحيات وتدقيق effective permissions؛ أي قدرات جديدة تحتاج موافقة وتصميمًا أمنيًا مستقلًا |
| لاحقة | شاشة Customers غير موجودة والمحرك المالي ليس دفتر صرف | لا تعاد روابط أو أزرار لميزات غائبة؛ يحدد المنتج/backoffice متطلبات مستقلة إذا أُريد بناؤها |

الإبقاء على ست مجموعات رئيسية وروابطها السياقية هو التنظيم المقترح والمطبق الآن. إخفاء قوائم WCFM القديمة اقتراح مستقبلي فقط وفق بوابات التقرير، وليس جزءًا من RC4.
