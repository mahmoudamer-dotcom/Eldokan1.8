# تقييم اعتماد Admin Staff على WCFM — قراءة فقط

النطاق: Admin Staff rc.1 المرفق مع المحافظة عليه في rc.2. لم يُرفق مصدر Seller Dashboard API أو مصدر WCFM لهذه المهمة، ولم تُعد مراجعة RC1/RC2 التاريخية. النتائج أدناه تخص المصدر المتاح، ولا تشهد بجاهزية إيقاف WCFM.

## مؤكد من المصدر

| الاعتماد | الموقع / الوظيفة | أثره |
|---|---|---|
| أدوار `wcfm_vendor` و`vendor` و`seller` واكتشاف أدوار WCFM المثبتة | `seller_roles`, `owner_users`, `wcfm_role_choices`, `wcfm_migration_roles` | إدراج التجار وتعيين دور WCFM عبر WordPress؛ دور الدكان محفوظ إلى جانبه |
| `wcfmmp_profile_settings` ونسخته السابقة واسم المتجر وساعات العمل والشحن والسياسات وSEO | `company_name`, `wcfm_store_settings`, `wcfm_migration_company_name` | fallback لأسماء المتاجر وقراءة/نسخ تاريخ إعداداتها |
| `_wcfm_vendor_id` و`vendor_id` و`_vendor_id` و`post_author` | `wcfm_source_product_ids` | اكتشاف الملكية السابقة أثناء الربط |
| الدالة `wcfm_get_vendor_id_by_post` عند توافرها | `wcfm_source_product_ids` | محلل ملكية اختياري للقراءة أثناء اكتشاف المنتجات |
| جدول `{prefix}wcfm_marketplace_orders` وعمود `vendor_id` | `wcfm_marketplace_order_rows` | استخراج تاريخ بنود طلبات البائعين |
| اكتشاف جداول `%wcfm%` وصفوفها المرتبطة بالتاجر | `wcfm_tables`, `wcfm_index_vendor` | نسخ تاريخي إلى فهارس الدكان مع استبعاد المفاتيح الحساسة |
| فهارس `{prefix}eldokan_wcfm_*` | `wcfm_snapshot`, `seller_detail` وصفحة الفهرس | جداول يمتلكها الدكان، لكنها تحتوي تاريخًا مستمدًا من WCFM؛ ملف التاجر يستخدمها لتفاصيل التاريخ |
| أدوار بائع/WCFM ضمن منع الوحدات الحساسة | `ElDokan_Operational_Modules::staff_capabilities` | منع فتح الدفع والقصص بمجرد امتلاك دور بائع |
| أدوار WCFM واسم متجر قديم في منتقي القصص | `ElDokan_Stories_Picker::sellers` | العثور على التجار؛ تفاصيل البطاقة تأتي من Customer API |

لم يظهر استدعاء مباشر لفئة WCFM أو تسجيل خطاف خدمة خاص به داخل Admin المرفق. توجد دالة الملكية الاختيارية المذكورة، واعتمادات بيانات وأدوار واضحة. أسماء AJAX التي تبدأ `eldokan_wcfm_*` هي معالجات الدكان نفسها وليست دليلًا على تنفيذ WCFM لها.

## ما ينفذه الدكان بنفسه

حالة التسجيل والاعتماد، ربط حساب الشركة، حالة وصول التاجر، قوالب صلاحيات لوحة التاجر، أدوار الموظفين، التقييم الداخلي وتقييم الإلغاء، قواعد العمولة وأولويتها ولقطات رسوم بنود الطلبات، التقارير وكشوف الحساب وسجل النشاط والبريد. الملكية الدائمة تستخدم `_eldokan_seller_user_id` في المنتجات وبنود الطلبات، مع fallback إلى المؤلف/المالك. الطلبات نفسها تُقرأ وتُحدّث عبر WooCommerce. إدارة الرئيسية والقصص وإعداد محول الدفع وحدات مستقلة داخل الدكان، مع تكاملاتها الحالية.

هذه الاستقلالية لا تثبت وجود بديل كامل للمحاسبة متعددة التجار أو عمليات التسوية والتحويل. حساب صافي المستحقات في تقرير ليس نظام صرف وتسويات.

## ما يخص Seller API ويحتاج مراجعة لاحقة

مصدر Seller API غير متاح هنا، لذلك لا يجوز نسبة اعتماداته إلى Admin أو تأكيد زوالها. يلزم فحص مستقل لمصادر أدوار `eldokan_owner` وفريق التاجر، محلل الملكية عند الكتابة، صلاحيات المنتجات، توزيع الطلبات وحالات تنفيذ التاجر، حساب/تجميد العمولات والمرتجعات، طلبات السحب والصرف والتسوية، شحن التجار وضرائبه ورسائله ومهامه الخلفية. يلزم أيضًا تتبع تنفيذ Customer API Sellers/Products المستعمل في منتقي القصص؛ لم تتغير هذه التكاملات.

## ما يبقى أساسيًا تشغيليًا

الملكية القديمة والمصدر التاريخي للدور/المتجر/الطلب أساسية للفهرسة والربط الحاليين. الاعتماد الفعلي على WCFM في حساب العمولات التشغيلية والسحب والتسوية والشحن لا يمكن حسمه من Admin وحده. تبقى خدماته مفعلة حتى وجود بديل مختبر ومطابقة أرصدة ومرتجعات وعمولات وتاريخ طلبات. WooCommerce وحده ليس إثباتًا لوجود بديل لكل خدمات السوق متعددة التجار.

الرسالة القديمة «Ready to Remove WCFM» تفحص روابط بيانات فقط. **اجتيازها ليس شهادة بأن التسويات والشحن والصلاحيات والتكاملات جاهزة لإزالة WCFM.** لم تُغير آلية الفحص أو تُشغل في هذه المهمة.

## إخفاء الشاشات القديمة

يمكن لاحقًا دراسة إخفاء روابط قائمة WCFM للموظفين الذين يغطّي الدكان مهامهم بالكامل، مع إبقاء خدمات الإضافة وخطافاتها وأصولها المطلوبة. إخفاء رابط لا يوقف خدمة ولا يمنع الدخول المباشر؛ ضبط الوصول يجب أن يظل عبر capabilities. لا يمكن اعتماد قائمة صفحات آمنة بعينها من هذا المصدر وحده. لم تُخفَ أو تُعطّل أي صفحة WCFM هنا، ولا ينبغي حجب واجهات الشحن أو السحب أو العمولة قبل توثيق البديل.

## مسار تخفيض الاعتماد

1. حصر عملي لخدمات Seller API وWCFM المستخدمة حيًا دون تعديلها، وتحديد مالك كل بيانات وتدفق.
2. مطابقة الملكية والتاريخ وقواعد العمولة والمرتجعات وأرصدة التجار، مع الاحتفاظ بالسجلات الأصلية.
3. عزل القراءة عبر واجهة توافق داخلية، ثم مقارنة النتائج القديمة والجديدة على التجريبي دون كتابة مزدوجة غير منضبطة.
4. استبدال كل خدمة منفصلة، خصوصًا الشحن والتسوية والصرف، بعقد واختبارات قبول وتراجع واضحين.
5. إخفاء القوائم التي ثبت الاستغناء عنها، ثم إيقاف الوحدات تدريجيًا بعد قبول حقيقي. عدم حذف جداول WCFM حتى اكتمال المطابقة والاحتفاظ التاريخي.

لم يُنفّذ شيء من هذا المسار في مرشح الواجهة.
