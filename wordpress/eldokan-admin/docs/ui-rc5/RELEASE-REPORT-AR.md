# RC5 — تقرير التثبيت الوظيفي المختصر

التاريخ: 19 أكتوبر 2026. الأساس RC4: `b79de4097601e45c8aae2d9ecc8296647f14f50f`.
**مرشح اختبار مستقل 1.10.0-rc.5، غير معتمد للإنتاج. لا نشر أو اتصال بقاعدة Live.**

## المشاكل المؤكدة والإصلاحات
1. ملكية الطلبات: استكمال الإصلاح السابق ضمن RC5؛ canonical البند ثم `_eldokan_seller_owner` الرقمي المعروف، ثم fallback السابق للعرض والفلترة فقط. لا اعتماد على الاسم أو كتابة/إصلاح للطلبات. السبب الدقيق للطلب #22862 غير محسوم؛ استعلاماته السبعة محفوظة في `order-22862-readonly.sql` كقبول مؤجل.
2. بطاقة العملاء: كانت بلا وجهة؛ أصبحت تفتح صفحة حسابات customer/subscriber مجزأة إلى 50 حسابًا بالبحث، بنفس تعريف العدد. الصفحة والبطاقة تتطلبان `list_users` دون منح صلاحيات جديدة، ولا تشمل مشتريات الزوار.
3. Pending: Dashboard كان يستخدم wp_count_posts بينما القائمة تستخدم WP_Query المفلترة لغويًا. أصبح العد والقائمة يستخدمان سياسة WP_Query واحدة، بنفس اللغة والحالات وبقاء WPML filters. «جميع الحالات» تضم الخاصة أيضًا؛ كل ترجمة سجل مستقل، ولا ندّعي عدد منتجات تجارية فريدة. مقدار اختلاف Live نفسه يحتاج قبول WPML الفعلي.
4. حفظ عمولة المنتج: حفظ/تعطيل/حذف يحتفظ بالبحث والتصنيف والحالة واللغة والصفحة ويعود إلى صف المنتج. البحث يُرمّز في الروابط، وتظهر حالة نجاح بعد تأكيد الحفظ فقط. عند الفشل رسالة واضحة ورجوع للنموذج، دون نجاح كاذب؛ مُنع إرسال النموذج مرتين مع دعم Browser Back.
5. حماية قواعد العمولة: المصدر كان يعطل القديمة قبل التأكد من إدخال البديلة. أصبح الإدخال والتعطيل عملية transaction مع فحص جميع النتائج والـcommit/rollback، وتبقى نسخ القواعد السابقة في الجدول مع حالتها. تُرفض المدخلات/الأهداف غير الصالحة بدل تحويلها إلى قاعدة عامة عرضًا. 0% قاعدة صالحة تتقدم حسب الأولوية، وليست غياب قاعدة.
6. التصنيفات: حفظ/مسح term fee ومرآتها في جدول القواعد ذريّان. حذف mirror وحده لا يزيل مصدر term meta؛ أصبحت الإدارة توجه إلى Clear Fee بدل نجاح مضلل. التعطيل يبقي السجل، والحذف يخص السجل المحدد؛ كلاهما محمي بالصلاحية والـnonce.
7. الواجهة: حالة Enabled/Disabled واضحة، وأفعال الحفظ والحذف مخفية عن قارئ العمولات فقط. سجل القواعد الرئيسي 50/صفحة وملف التاجر يعرض آخر 100 نسخة بوضوح. تنظيم وfocus وحالة الحفظ وRTL وعرض الهاتف تحسنت دون إعادة بناء. إصلاح fragment غير صالح كان يمكنه إيقاف JS في ملف التاجر. أضيفت ترجمة الرسائل الجديدة مع الحفاظ على الترجمات السابقة.
8. الأداء: cache داخل الطلب فقط لنتيجة العمولة وتصنيفات المنتج وعدّ المنتجات وعدّ التسجيلات، وإعادة استخدام عينة WooCommerce الأكبر بدل استعلام ثانٍ مكافئ. لا cache دائم جديد ولا تعديل قواعد البيانات/الفهارس أو سلوك WCFM.

## ثوابت محفوظة
ترتيب الأولوية نفسه: Seller Product > Seller Category > Seller All > Global Product > أعمق تصنيف مفعّل عبر term meta > legacy Global Category > Global All. قواعد الصفر تتوقف عندها عملية الاختيار مثل غيرها، والمعطلة مستبعدة. القواعد الجديدة لنفس النطاق/الهدف تستبدل النسخة المفعلة دون حذف تاريخها. تعطيل/حذف override يكشف القاعدة المطابقة التالية؛ لا مساواة بين 0% والتعطيل.

43 دالة محمية من RC4 مطابقة، تشمل REST routes وحالات WooCommerce وfee snapshots وتهيئة schema ومسارات WCFM. ملفات Home وroles وcategory attributes وPDF والـloader والوحدات المدمجة مطابقة بايتًا لـRC4. لا تعديل Customer API أو Seller API أو WCFM أو مخططات/جداول أو بيانات/سجلات تاريخية.

## نتائج الاختبارات وحدودها
- PHP 8.3.35 محمول من المصدر الرسمي، تم التحقق من SHA-256 للأداة قبل استخدامها. PHP lint: 15 ملفًا؛ JS syntax: 4 ملفات.
- 256 تحققًا في RC5 regression على الدوال الفعلية بمخازن WordPress/DB اصطناعية، و32 fixture ملكية/96 تحققًا؛ مجموع تحققات PHP: 352.
- رفض الوصول للـ17 renderer المسجلة و34 admin-post/AJAX رئيسية، واختبار الطلبات غير الصالحة والـnonce؛ حراس الوحدات الأخرى مشمولون. راجع PAGE-MATRIX.md.
- bootstrap في 4 أوضاع: عادي، legacy Checkout، legacy Stories، وإيقاف الوحدتين، ثم إعادة تضمين ملف الإضافة للتحقق من منع تعارض النسخة.
- Chrome headless: 57 تحققًا، 4 صفحات فعلية الرسم ببيانات اصطناعية، ar/en وRTL/LTR بأبعاد 1440/768/390، دون overflow عام أو أخطاء JS؛ حفظ القيم وbusy/Back والتأكيد والإلغاء. لا اتصال HTTP بخلفية WordPress.
- نموذج DB يثبت ترتيب نداءات transaction والتراجع ضمن النموذج؛ **لا يثبت InnoDB أو تعارض عمليتين أو hooks طرف ثالث على موقع حقيقي**. اختبارات الـbootstrap لا تنفذ init/admin_init أو migrations.
- التحليل غطى تسجيل الصفحات والصلاحيات ومسارات الكتابة، لكنه لا يُساوي قبولًا ناجحًا لكل الوظائف على WordPress. لقطات المتصفح مع بيانات اصطناعية ليست صور Live.

## المطلوب قبل التثبيت
1. على clone حديث معزول من الموقع: أكد WP/PHP/WooCommerce/HPOS/WPML/WCFM/Paymob وslug الحالي، وخذ backup قابلًا للاستعادة من الملفات والـDB. لا Full Deploy من staging.
2. تحقق قراءة فقط أن جدول commission rules وtermmeta يعملان بـInnoDB ويدعمان transactions. RC5 يرفض الحفظ إن تعذر إثبات ذلك، ولا يحوّل المحرك أو يشغّل migration. افحص اكتمال schema/role initialization الموروثة قبل تجربة الإدارة.
3. نفذ مصفوفة الصفحات بحساب مدير وموظفين محدودين، والروابط المباشرة والـaliases وar/en وStories الأصلي/media picker وHome وCheckout settings. لا تعطّل الإضافات القائمة.
4. طابق Pending في Dashboard والقائمة لنفس WPML language/status/category/search؛ اختبر private وtranslations والصفحات التالية. اختبر الوجهة المحمية للعملاء دون منح موظف جديد list_users.
5. على DB الاختبار فقط: حفظ/استبدال 0% وfixed/hybrid؛ Seller/Global/Product/Category precedence؛ تعطيل/حذف/clear؛ إخفاق insert/update/commit/meta، عمليتا حفظ متزامنتان، وفحص caches/hooks. تأكد أن old rules وfee snapshots والطلبات السابقة لا تتغير عند الفشل. افحص سلوك المرآة مع إضافات WPML وغيرها.
6. سجل PHP errors وquery count وTTFB لنفس طلبات WordPress القياسية ثم Dashboard/Products/Reports وبحجوم حقيقية. حدود عينات 300/150 طلب وقوائم/تقارير تاريخية باقية؛ لا ننسب بطء WordPress كله إلى هذه الإضافة دون قياس. admin_init schema checks والتقارير التاريخية قد تبقى مكلفة؛ لم نغيّر مسارات التهيئة أو WCFM.
7. نفذ الاستعلامات السبعة للطلب #22862 قراءة فقط عندما تتوفر البيانات، ولا تكتب metadata أو تستنتج الهوية من اسم I-Technology. افحص النتائج المكررة وProduct/Variation IDs والمالك الحالي وparent mapping قبل تقرير السبب.

## غير محسوم وممنوع ادعاء إصلاحه
- السبب الحقيقي للطلب #22862، namespaces مفاتيح vendor الأخرى، وتغيّر الفريق/ملكية المنتج تاريخيًا. إصلاح العرض لا يعمم تلقائيًا على تقارير المال أو Checkout؛ هذه المسارات المشتركة بقيت كما كانت.
- عيوب تعريف العينات/المؤشرات وفجوات هوية APIs الموثقة سابقًا ليست مقبولة ماليًا ولم تُعد كتابة خدماتها. لا WCFM retirement ولا اعتماد أرصدة/صرف.
- لا WordPress/DB integration أو SiteGround acceptance أو قياس سرعة موقع حقيقي. أي hooks خارجية قد يكون لها أثر لا يغطيه rollback نموذج DB.

## التثبيت والرجوع بعد اجتياز القبول والموافقة
استخدم INSTALL ZIP فقط، بنفس `eldokan-admin/eldokan-admin.php` عبر Replace current with uploaded، دون uninstall أو إنشاء إضافة ثانية. احتفظ بملفات الإضافة المثبتة الفعلية للرجوع. عند خلل: استبدل مجلد الإضافة كاملًا بالنسخة السابقة بلا بقايا، ثم افحص الإصدار والسجلات والصلاحيات. الرجوع بالملفات لا يلغي كتابة بيانات؛ لا تُستعد DB قديمة فوق طلبات أو دفعات حديثة. لا تنفيذ checkout حي أو refunds أو repair/migration ضمن smoke test. النسخة غير معتمدة للإنتاج.
