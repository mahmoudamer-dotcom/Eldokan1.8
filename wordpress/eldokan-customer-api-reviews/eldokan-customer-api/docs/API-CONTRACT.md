# Public API contract — Customer API 0.8.0 / Contract v1

Customer API backend **0.8.0**, Contract **v1**, Phase 2C code-complete. Client **0.6.0**, Developer Portal **1.8.0**, final OpenAPI and Mahmoud frontend handoff are complete. Real staging acceptance remains pending. Base path: `/wp-json/eldokan-customer/v1`. This is the current production release contract; checkpoint/recovery evidence is maintained separately. Native Paymob **4.1.15** hosted support is restricted to the audited safe Accept TRANSACTION POST profile.

## Transport, identity and errors

JSON success: `{ "success": true, "data": ..., "meta": { "request_id": "req_..." } }`. JSON failure: `{ "success": false, "error": { "code": "...", "message": "..." }, "meta": { "request_id": "req_..." } }`. Checkout and Order callbacks can additionally include `error.issues`. Readiness validation instead returns HTTP 200 with `data.ready:false` and `data.issues`; an unavailable/ambiguous payment after purchase can return HTTP 200 with `data.payment.issue` (placement) or `data.issue` (payment endpoint). Never interpret HTTP 200 alone as paid or redirect-ready.

All decorated responses, including public catalog responses, use **`Cache-Control: private, no-store`**. Public catalog can use private server-side application caching; account, Wishlist, Cart, checkout and Orders use cache BYPASS. Headers include `X-ElDokan-API-Version`, `X-ElDokan-Request-ID`, `Content-Language`, cache diagnostics and timing. All inventory rows inherit these transport/error/privacy rules. JSON request body is the supported mutation representation.

Auth labels used below:

- **P**: public, guest/customer readable; no CSRF.
- **L**: customer login only; native WordPress HttpOnly cookies; customer role only, excludes staff/seller accounts. Reads need no mutation CSRF. **L+** adds session-bound `X-ElDokan-CSRF`.
- **C**: current customer Cart or opaque HttpOnly Guest Cart session; reads restore/create Guest session as supported. **C+** adds current owner's `X-ElDokan-CSRF`; restore `/cart` or `/checkout` before mutation.
- **O**: authenticated native Woo customer owner OR exact Guest Order capability header `X-ElDokan-Order-Access`. **O+** adds customer session CSRF for account-owned Orders, or the dedicated Guest Order CSRF for capability-owned Guest Orders. A logged-in customer retaining a valid Guest capability may use it; this never attaches that Guest Order to the account. A staff/seller cookie cannot become a Guest through a capability.
- **A**: register/login public entry point, origin validation and rate limits; no existing mutation CSRF required. Session endpoint requires an authenticated customer and does not establish anonymous customer identity.

Private routes validate allowed origins where the service requires them. Credentialed CORS uses the trusted allowlist, exact origin, `Access-Control-Allow-Credentials:true`, protected `X-ElDokan-CSRF`, `X-WP-Nonce` and `X-ElDokan-Order-Access` headers. Use browser credentials; do not invent a Bearer-token flow. Native cookie/REST nonce behavior is preserved. Unknown/foreign Orders and invalid/missing Guest credentials share `order_not_found`/404; valid foreign addresses share `address_not_found`/404. Malformed public IDs return the validation error where route matching reaches the service; otherwise WordPress returns normalized REST no-route errors.

| Public identifier | Delivered syntax and treatment |
| --- | --- |
| `cus_*` | `cus_` + 32 lower-case hex, stable random customer identity |
| `adr_*` | `adr_` + 64 lower-case hex, random account Address Book identity |
| `cit_*` | `cit_` + 32 lower-case hex, random Cart line |
| `chk_*`, `ord_*` | prefix + 64 lower-case hex, durable purchase attempt / public Order |
| `shp_*` | `shp_` + 64 lower-case hex, keyed choice bound to current address, Cart and native shipping costs |
| `gok_*` | `gok_` + 64 lower-case hex, **secret credential**, exact one Guest Order; header only |
| `prd_*`, `var_*`, `sel_*`, `cat_*`, `brd_*`, `tag_*`, `att_*`, `atr_*`, `hsl_*`, `hbn_*` | existing opaque catalog IDs, currently decimal suffixes; clients must never parse them or send raw numeric IDs |

`lang=ar|en` is optional on catalog, Wishlist, Cart, checkout and Order routes. `Content-Language` is authoritative after fallback. WPML translations can have distinct catalog IDs; source Cart/Wishlist membership remains language-independent. Order historical snapshots do not become mutable translations. No Woo numeric Order ID, Order key, private commission, native gateway settings, provider transaction/internal IDs, API key or HMAC secret is public.

## Shared schemas

`Money = {amount:integer minor units,currency:string,decimals:integer,formatted:string}`; missing native product prices can yield null. Query min_price/max_price use **major units**. `Image = {url:string,alt:string}|null`. `Customer = {id:cus_*,first_name,last_name,display_name,email,phone:string}`. `Session = {customer:Customer,csrf_token:string}`. Register requires email/password (10–128 characters) and accepts optional first_name,last_name (100 characters), display_name (250 characters), phone:string (32 ASCII characters maximum). Phone is not mandatory; omitted/empty phone is valid. Phone validation and canonical storage are specified below. No roles/customer IDs/staff authorization are accepted.

`Address` includes `id:adr_*`, first_name,last_name,phone,email,company,country,state,city,street_address,address_extra,is_default. Create requires first_name,last_name,phone,email,country,state,city,street_address; country exactly EG, installed Woo governorate state code. company/address_extra nullable, is_default boolean (default false; first address becomes default). Byte limits: first/last100,phone32,email254,company150,country2,state32,city150,street/address_extra500. AddressBook is `{items:Address[],count,default_address_id:adr_*|null}`, maximum20. Unknown fields rejected. Updates cannot modify IDs/ownership. Delete promotes the deterministically ordered remaining address if the default was removed; missing/foreign is 404.

`Seller = {id:sel_*,name,slug,rating:null,rating_count:null}|null` in catalog. Only canonical `_eldokan_seller_user_id` plus accepted Seller role and configured business name establishes catalog Seller ownership. No employee/author inference. Historical Order Seller is smaller `{id:sel_*,name}` from the immutable placement snapshot, not today's Seller profile.

`Pricing = {price,min_price,max_price,regular_price,sale_price:Money|null,on_sale:bool,discount_percent:number|null}`. `Stock = {status:in_stock|out_of_stock|on_backorder,quantity:number|null,backorders_allowed:bool}`. ProductCard fields: id,slug,name,type,brand:Brand|null,pricing,stock,image,average_rating:number,rating_count:int,seller. ProductDetail has id,slug,name,type,sku:string|null,brand,categories:[{id,name,slug}],pricing,stock,image,delivery:{label:null,min_days:null,max_days:null},warranty:{label:string|null,duration:null,unit:null,type:null},seller,images:Image[],attributes,variations,short_description_html,description_html,average_rating,rating_count. Sanitized HTML only. Attributes: `{name,slug,id:att_*|null,visible,variation,options:[{id:atr_*|null,name,slug}]}`. Variations: `{id:var_*,attributes:VariationSelection[],purchasable,pricing,stock,image}`; use the advertised selection. VariationSelection is `{attribute_id:att_*|null,attribute_slug,option_id:atr_*|null,option_slug:string|null}`. Unsupported wildcard selections fail explicitly; no missing attribute guessing.

`Category = {id,name,slug,description:HTML,count,parent_id:cat_*|null,image}`. `Brand={id:brd_*,name,slug,image}`; Term for tags `{id:tag_*,name,slug}`. CategoryFilters `{category_id,source:{mode,category_id},attributes:[{id:att_*,name,slug,options:[{id:atr_*,name,slug}]}]}`; source mode configured, inherited, inferred_from_products, none or unavailable. No raw taxonomy internals. Absent brand/tag taxonomy returns an empty collection.

`HomeSection={id,type,enabled:true,order:int,title,items:[]}`. Types: hero_slider,banner_grid,category_grid,product_carousel,brand_grid. Editorial item `{id:hsl_*|hbn_*,kind:hero|banner,title,subtitle,desktop_image,mobile_image,cta:{text,type:url|product|category|search,value}|null}`. Only active published/localized/currently scheduled public items. No admin configuration/scheduling metadata is serialized.

ProductQuery: lang,page>=1(default1),per_page(default24,clamped1..48),search,category/brand/tag slugs,attributes,min_price/max_price>=0,stock_status,on_sale/featured booleans,sort newest(default)|price_asc|price_desc|best_selling|rating|relevance. min<=max. `attributes=att_1:atr_12,atr_13;att_2:atr_31`: category mandatory, OR within attribute, AND between attributes; maximum5 attributes/10 options each/500 encoded characters, all IDs advertised by category filters. Catalog lists only published, password-free, visible parent products; direct links can reach Woo hidden products but never private/draft/password protected products.

## Cart, checkout and purchase schemas

`Cart={items:CartLine[],count:int,valid:bool,owner_type:guest|customer,csrf_token:string}`. Mutations add `changed:bool`. Maximum100 lines. CartLine: id:cit_*,product_id,variation_id|null,name,image,selected_attributes:VariationSelection[],quantity,unit_price:Money|null,line_subtotal:Money|null,stock,seller,valid,issues:[{code,message}]. Membership/quantity persists independently of localized projection. Checkout's validated line issues additionally include blocking and optional item_id, and invalid selections can be retained with safe unavailable placeholders for correction. Repeated Wishlist add/missing removal returns changed:false; Cart duplicate adds of an existing compatible selection return changed:false without changing quantity; quantity update sets the quantity. Login merge combines compatible quantities subject to native bounds. No frontend price/seller/stock authority.

QuoteInput is exactly one of `{address_id:adr_*,shipping_method_id?:shp_*}` or `{address:CheckoutAddress,shipping_method_id?:shp_*}`. CheckoutAddress fields are first_name,last_name,phone,email,state,city,street_address,company,address_extra,country; same string boundaries as validation, country defaults EG, optional company/address_extra nullable. No is_default, id, postcode, numeric customer IDs or frontend totals. Guests cannot use address_id. Direct addresses are never saved to Address Book. GET /checkout may use the authenticated default saved address; Guest POST address is not remembered implicitly.

`Checkout={cart,ready,issues:[{code,message,blocking,item_id?}],address:CheckoutAddress (+id only if saved)|null,address_requirements:{country:"EG",required_fields,state_codes,required:true},saved_addresses:AddressBook,shipping_required,shipping_calculable,shipping_methods:ShippingChoice[],selected_shipping_method:ShippingChoice|null,payment_methods:PaymentChoice[],payment_availability_calculable,payment_required,totals,stock_reserved:false}`. Totals fields subtotal,shipping,tax,fees,discount,total use Money|null, plus taxes_enabled/calculable booleans. Native Woo Cart/totals/fee/tax/shipping engine owns arithmetic. Unknown destination totals are null; do not calculate final total from public card prices. ShippingChoice `{id:shp_*,name,description,amount:Money,available:true,type:pickup|door_delivery}`. Physical shipping requires a current selected whole-cart native choice; compatible pickup or delivery bundles only. No invented carrier rate.

PaymentChoice `{id:cod|paymob,name,description,available:true,requires_redirect:bool}`. Native filtered availability, restrictions, currency and configuration apply. A4 Paymob exposes only the configured audited native hosted gateway, excludes Pixel/subscription/custom overridden implementations, and requires the trusted safe callback profile/front-end origin. COD does not require Paymob configuration.

PurchaseInput: exactly one address mode, required shipping_method_id (current shp_* for physical shipping; explicit null if not required), required payment_method cod|paymob, optional order_notes UTF-8 text <=1000 characters and <=4000 raw bytes. Placement additionally requires checkout_attempt_id:chk_*. No payment credential/status/transaction/total fields. Preparation does not create/reserve an Order. The attempt binds owner/session and final validated Cart,address,Seller,prices,stock,shipping,fees,discounts,totals and selected native Paymob gateway. Changing input on the same attempt returns conflict; changed final material returns checkout_changed/409; refresh quote/review deliberate new purchase before preparing a new attempt. Uncertain committed purchase/recovery is **not** permission to make another attempt.

Placement base receipt has exactly order_id,checkout_attempt_id,status,payment_method:{id,name,requires_redirect},total:Money,currency,lines:[{name,quantity,subtotal,total,seller:{id,name}}],shipping:ShippingChoice|null,created_at. The accepted receipt's **status is its native placement-time Woo status**, not the new normalized live status. Replays preserve that immutable receipt. Authenticated COD receipt remains unchanged. Guest placement additionally returns `guest_access:{credential:gok_*,csrf_token,header:"X-ElDokan-Order-Access"}`. Paymob placement additionally returns `payment:Payment` or safe committed-Order follow-up issue. Always retain ord_* before navigating; never repeat purchase with a new chk_* solely because hosted initiation failed.

The purchase creates/reuses ONE native Woo Order, atomic mapping/snapshots/receipts/Fulfillments, existing native fee hooks and native stock lifecycle. Native COD executes its accepted path; Paymob starts as native pending/unpaid with native reservation behavior. All purchase state COMMITs, transaction ends and global placement lock is released/verified before native gateway process_payment. Initiation errors never replay checkout hooks, reduce stock again or generate child Orders.

## Live Orders, payment and Guest access

OrderSummary exact fields: id,created_at,updated_at,status,payment_status,payment_method,currency,total:Money,item_count (sum of quantities),shipping:ShippingChoice|null,fulfillments:[{seller:{id,name},status}]. List is **Phase 2C mapped completed purchase records only**, sorted created_at descending then public Order ID descending. Native Woo account ownership, not login-session hash, controls history. Guest capability never authorizes list. Arbitrary customer_id parameters confer no authority. Legacy unmapped Woo Orders are omitted, no migration/sequential IDs.

OrderDetail exact fields: id,created_at,updated_at,status,payment_status,payment_method,currency,subtotal:Money,discount:Money,fees:[{name,total:Money,tax:Money}],shipping_total:Money,tax:Money,total:Money,address:CheckoutAddress,lines:[{product_id:prd_*,variation_id:var_*|null,name,quantity,subtotal:Money,total:Money,tax:Money,seller:{id:sel_*,name}}],item_count,shipping:ShippingChoice|null,order_notes:string,fulfillments. Address/Seller/name snapshots remain historical; financial/status fields read the current authoritative Woo Order. Money uses historical currency and purchase decimal precision. Native customer-visible fee items are exposed; private commission/internal Paymob adjustment metadata is not manufactured into a breakdown. No product thumbnail is promised for historical Order lines.

Stable status vocabulary: pending_payment,processing,awaiting_pickup,shipped,delivered,cancelled,failed,refunded. Default mapping: pending→pending_payment; processing/on-hold→processing; cancelled/failed/refunded→same. **completed and unknown custom native statuses require explicit verified configuration** in `eldokan_customer_api_order_status_map`; do not assume completed means delivered. Missing mapping gives order_read_unavailable/503 (and payment follow-up issue where projection fails). Allowed mapping values are the stable vocabulary; pending/cancelled/failed/refunded cannot be overridden. Per-Seller Fulfillment internal pending→public pending by default; other operational states require `eldokan_customer_api_fulfillment_status_map`. Fulfillment summaries are independent; A4 does not derive aggregate delivery from them or provide Seller mutation. Stage with actual Admin/Seller semantics before selecting mappings.

Payment status precedence: native refunded→refunded, cancelled→cancelled, is_paid()→paid, failed→failed, on-hold→pending, otherwise unpaid. Native Woo paid semantics also apply to COD; this is not a separate cash-collection confirmation.

`PaymentInput={}` (recover/reuse current state), or `{retry:true,expected_generation:nonnegative JSON integer}` for explicit new native initiation when a valid redirect cannot be recovered. Only retry boolean and expected_generation are accepted. A valid unexpired cached session is reused even on explicit retry; expired/unknown/ambiguous/initiating state requires current generation confirmation. Stale expected_generation cannot create another session; concurrent matching retries serialize per Order and reuse the new ready result. This is **API initiation fencing, not provider idempotency or a promise to cancel older provider sessions**.

Normal Payment fields: order_id,order_status (normalized live status),payment_status,payment_method:"paymob",requires_redirect:boolean,redirect_url:string|null,retryable:boolean,generation:int,expires_at:ISO8601|null, optional issue. Eligibility: original Paymob-concept native Order, owner/capability, unpaid, needs_payment(), pending|failed, native hosted gateway still eligible. Already paid returns current state with no provider call. Cancelled/refunded/no-longer-needs-payment returns nonretryable payment_not_eligible. COD Orders cannot be switched through this endpoint. No public payment ID.

Issues in successful Payment: payment_retry_confirmation_required (show deliberate retry, send observed generation), payment_initiation_unavailable (provider result uncertain; read the same Order, deliberate retry only), payment_not_eligible. Placement may use minimal `{order_id,requires_redirect:false,redirect_url:null,retryable:true,issue}` when a post-COMMIT gateway/storage/projection issue prevents the normal fields, including order_followup_unavailable. Resolve by reading/retrying the SAME Order, or original checkout owner repeating the SAME chk_* for receipt/Guest-credential redelivery. An HTTP payment error is not purchase rollback.

Redirect is validated against the selected native gateway's public-key region and exact HTTPS `/unifiedcheckout/` route on accept.paymob.com,uae.paymob.com,pakistan.paymob.com,ksa.paymob.com or oman.paymob.com. Only native publicKey/clientSecret query fields are accepted; no userinfo, fragment, arbitrary host/path/port/extra return destination. The complete hosted URL necessarily contains a session capability intended for this authorized payer. It is encrypted at rest with AES-256-GCM, never exposed outside owner payment results or included in purchase proof, and must not be logged/shared/cached by clients. No separate merchant secret is copied into API storage. Expiry is captured from the native intention payload when reliable; no invented expiry if unknown. An unknown expiry prevents automatic later cache reuse.

Guest capability has 256-bit cryptographic strength derived from a random public Order, exact owner binding and server secret; only its SHA-256 digest is stored. Send it solely in `X-ElDokan-Order-Access`, plus `guest_access.csrf_token` in `X-ElDokan-CSRF` on payment mutations. It works for exactly that Guest Order independently of the Cart cookie. Email/phone/ord_*/Woo key/query fields never authorize access; no account attachment by email. It is delivered/redelivered only by original authorized checkout placement retry, never by list/detail. No public expiry/revoke endpoint is introduced. Server secure-auth key rotation invalidates redirect decryption and credential rederivation; a previously delivered Guest credential still matches its stored digest. Operations must retain safe server keys/backup policy, never fall back to plaintext or alternate identity recovery.

## Original Paymob callback and return boundary

No new Customer API webhook exists. Native plugin owns `?wc-api=paymob_callback` / action `woocommerce_api_paymob_callback`, HMAC verification, callback handling and Woo status/stock changes. A4 supports the **native Accept TRANSACTION POST profile** (`eldokan_customer_api_paymob_callback_profile=accept_transaction`), requires strict signed-field booleans and durable native provider-order→exact-Woo-Order binding before the original plugin verifier. The read-only admission guard does not calculate signatures or mark Orders paid. Invalid native HMAC is still rejected by native 4.1.15. Older accepted initiation generations retain bindings for legitimate delayed native callbacks; event ordering remains native plugin/Woo authority.

Source contradictions: native GET return mutates total/failed before HMAC and can complete payment from browser; native Accept signs provider Order ID but not merchant_order_id; native Flash signs amount+intention ID but not success/status; native boolean normalization can differ from truthy refund handling. A4 bypasses GET mutations for Phase 2C Orders, binds Accept provider identity to the correct Order and rejects unsafe Flash/type/unsigned refund overrides. **A merchant installation supporting only Flash is not an accepted A4 payment environment; keep Paymob unavailable.** Do not enable the profile based on a guessed configuration or replace it with direct provider calls.

The guarded browser return uses only a fixed trusted HTTPS origin plus `/orders/{ord_*}`, HTTP303, no access token/status/transaction query. Configure `eldokan_customer_api_frontend_origin` as an origin only, never from incoming Host/Origin. Browser return performs no total/status/stock write and is never proof of payment. Frontend reads protected Order detail before displaying payment success, handles pending/delayed POST callback, and must retain Guest capability before navigation. Actual native Sandbox response `intention_order_id` matching Accept signed `obj.order.id`, callback profile, expiry and real browser behavior require staging evidence.

## Error and downstream integration guidance

401 authentication_required/cart_session_required: restore appropriate session. 403 invalid_csrf_token/origin_not_allowed: restore token/check configured origin and customer role. 400 malformed IDs/pagination or normalized REST argument error. 404 unknown/foreign resource. 409 checkout_attempt_conflict/checkout_changed: review changed checkout; checkout_busy can be service-unavailable depending on the storage guard. 422 schema/native eligibility/selection correction. 429 too_many_attempts: respect rate limit. 503 storage/native calculation/read/recovery unavailable: retain chk_*/ord_* and escalate store recovery when specified, never invent a new purchase after an uncertain COMMIT.

Client/Portal/OpenAPI implement exact envelopes, complete alias methods, nullable Money/choice fields, two pagination locations (catalog meta vs Orders data.pagination), explicit generations and minimal placement follow-up issues, session/Guest-specific CSRF, historical receipt vs live normalized status, safe pending UI, and header-only Guest capability. Do not create a browser return payment verifier or infer delivered/paid from redirect/status query. ## Private Customer phone contract

Customer's exact public account schema is now `{id,first_name,last_name,display_name,email,phone}`. **`phone` is always a string; absent/empty canonical phone is `""`**, consistently in registration/login/session Customer projections and GET/mutation /me. Existing records need no migration. This is private account PII, never a public catalog field and never an authentication identifier.

POST /auth/register adds optional `phone:string`. Omitting phone remains valid and does not trigger a new required field or migration. Explicit empty string (or spaces only within the raw32-character limit) means empty optional phone. Registration shipping/billing address fields are not introduced. A later frontend may require a phone in its UX without changing this optional backend contract. GET /auth/session remains `{customer:Customer,csrf_token:string}` using existing native HttpOnly cookie/customer-role behavior. Email login remains unchanged and includes the same private phone projection; no lookup/login/password recovery/merge/Guest attachment by phone, no OTP/SMS/verification semantics.

POST,PUT,PATCH /me accept the exact whitelist first_name,last_name,display_name,phone. At least one supported field is needed. Phone-only update calls the native customer phone setter/storage; it does not submit unrelated name/email fields to WordPress. Omitted phone preserves the current value. Valid nonempty phone saves, `""` clears; **null is rejected**, including registration. Numeric JSON, arrays, objects and booleans are rejected. All requested phone and name fields validate before any write. Unrelated email/role/billing_address/billing_phone/meta_data fields remain unsupported. This is an ordinary partial profile update, not a new multi-resource transaction: a native storage failure is an error and can leave already-written requested name fields; restore GET /me before deciding what to retry.

Validation is identical for registration and profile updates: raw input must be a string <=32 ASCII characters, allow only ASCII digits, optional leading `+`, spaces, parentheses and hyphens; at least6 digits after ignoring allowed formatting. Surrounding **spaces** are trimmed; permitted interior formatting is retained and server-side sanitized. Tabs/newlines/Unicode digits/letters/extensions/HTML/embedded or repeated plus signs/oversize/fewer-than6 digits are rejected; arbitrary text is never stripped into a guessed phone. No country-specific mobile prefix requirement. Validation issue `invalid_phone` is422 at the service boundary; WordPress REST string-type validation can return its normalized argument error400 before service execution.

Canonical storage is native `WC_Customer(customer_id,false)->get_billing_phone('edit')`, `set_billing_phone`, `save`, with acknowledged value reread. No new schema/phone table/custom phone meta/duplicate storage. If Woo is absent, the preserved WordPress-only auth fallback accesses the **same canonical `billing_phone` user-meta key**, never a parallel phone field. Reads sanitize existing canonical values; old native billing phone can therefore already populate profile without migration. A read/save failure returns generic `phone_storage_unavailable`/503 through the standard error envelope, without echoing the phone or serializing an error as a Customer.

Registration validates phone **before account creation**. If canonical phone persistence fails after native account creation,503 is returned before creating an authenticated registration cookie; the native email account may already exist, just as other nontransactional registration storage failures can leave an account. Do not infer duplicate-account permission: recover using existing email login/session and then /me; phone is optional and does not become identity. No new automatic rollback/deletion/account matching or phone recovery endpoint is introduced.

Profile billing phone and saved adr_* address phone are independent concepts. Neither update rewrites the other. Current A1–A4 checkout takes its authoritative selected/direct address as before, not current profile phone. Existing native Order snapshots/notes/Seller snapshots/stock/receipts/Fulfillments/Guest capability/payment state remain unchanged. Authorized Order detail continues exposing the historical checkout phone actually used in that immutable address. Account phone never leaks into Order list/payment projections, Products, Seller profile, Home or public catalog. Matching account/Guest phone never attaches Guest Orders to accounts.
